# 文档写作规范

> 状态：Active
> Owner：{{OWNER}}
> Last Updated：{{YYYY-MM-DD}}

本文档定义项目文档的统一写法，用于保证不同项目、不同阶段、不同作者输出的文档保持一致风格。

## 1. 基本原则

### 1.1 先结论，后细节

每份文档开头优先回答这几个问题：

- 这份文档是干什么的
- 当前结论是什么
- 边界在哪里
- 谁需要看它

### 1.2 一文一主题

一份文档只解决一个核心问题。例如：

- 接口文档只写接口
- 数据库设计只写表结构与关系
- 风险文档只写风险与缓解措施

### 1.3 当前事实与未来计划分离

- **当前已确定/已实现**：写进正式文档
- **未来考虑/候选方案/待验证点**：写进 `BACKLOG.md` 或 ADR

## 2. 统一头部模板

除 `CHANGELOG.md` 外，建议每份文档顶部统一加：

```markdown
# {{DOC_TITLE}}

> 状态：Draft / In Review / Active / Deprecated / Archived
> Owner：{{OWNER}}
> Last Updated：{{YYYY-MM-DD}}
> Scope：{{SCOPE}}
> Related：{{RELATED_DOCS}}
```

占位符格式见 § 3。

### 2.1 例外

- **索引 / 导航型 README**（如 `docs/README.md`、`docs/adr/README.md`、`docs/features/README.md`、`docs/devlog/README.md`）**可省略** `Scope` 与 `Related` 字段：这类文档本身就是目录索引，Scope 等于"整个子目录"，Related 等于"目录下全部文件"，再填反而冗余。
- 但 `状态 / Owner / Last Updated` 三项**必须**保留。

## 3. 占位符规范

所有模板文件中需要使用者替换的内容统一使用 `{{PLACEHOLDER_NAME}}` 格式。

### 3.1 命名规则

- **必须**使用双花括号包围：`{{NAME}}`
- **必须**使用大写 + 下划线（SCREAMING_SNAKE_CASE）：`{{PROJECT_NAME}}`、`{{API_VERSION}}`
- **必须**语义明确，禁止 `{{X}}`、`{{TODO}}` 这类无信息名
- **禁止**混用 `[xxx]`、`<xxx>`、`{{xxx}}`、全角括号等其他形式
- **例外**：`text` 代码块中的 ASCII 示意图（架构图、ER 图、页面布局）可沿用 `[框体名]` 表示框，不视为占位符；此时必须通过 ```` ```text ```` 代码块包裹以明确语义

### 3.2 必填 vs 可选

在占位符所在行末或字段表"说明"列标注：

- 默认**必填**，不标注
- 可选字段明确标注 `（可选）`
- 条件必填字段标注 `（若 XX 则必填）`

示例：

```markdown
> Owner：{{OWNER}}
> Reviewer：{{REVIEWER}}（可选）
> Related ADR：{{ADR_ID}}（若涉及架构决策则必填）
```

### 3.3 常用占位符参考

| 占位符 | 含义 | 示例值 |
|--------|------|--------|
| `{{PROJECT_NAME}}` | 项目名 | `order-service` |
| `{{MODULE_NAME}}` | 模块名 | `payment` |
| `{{OWNER}}` | 责任人 | `张三` |
| `{{YYYY-MM-DD}}` | 日期 | `2026-04-17` |
| `{{VERSION}}` | 版本号 | `v1.2.0` |
| `{{ADR_ID}}` | ADR 编号 | `ADR-007` |
| `{{MILESTONE_NAME}}` | 里程碑名称 | `v1.0-发布` |

### 3.4 模板填写示例约定

每个模板文件**应该**在末尾附一个"附录：填写示例"章节，约束如下：

- **必须**使用 `## 附录：填写示例` 作为章节标题（便于检索与一致性）
- **必须**与主模板内容**通过清晰的分隔线或章节标题**分开，避免被当作模板的一部分复制
- 示例**应该**尽量短小（1–2 个典型条目即可），重点展示字段"填成什么样子"而非穷举
- 示例中的项目名、角色名、日期等**应该**使用脱敏占位（如 `示例项目`、`张三`、`2026-04-17`），不要使用真实内部代号
- 示例条目不使用 `{{XXX}}` 占位符，展示真实填写后的效果
- 对于规格极小、自解释的模板（如 `README.md`、`style-guide.md` 本身），可不附示例

## 4. 标题层级规范

- `#`：文档标题，只能出现一次
- `##`：一级章节
- `###`：二级章节
- `####`：必要时才使用
- 不建议超过四级标题

## 5. 推荐章节结构

推荐顺序：

1. 目的 / 背景
2. 范围 / 边界
3. 结论 / 规则
4. 细节说明
5. 示例 / 表格 / 附录

## 6. 术语与表达规范

### 6.1 表达要求

- 用短句，不写过长复合句
- 少用口语化表达
- 同一概念全篇用同一个名字
- 结论性语句优先使用：**必须 / 应该 / 可选**

### 6.2 避免的问题

- “这里大概是……”
- “后面可能会……” 写进正式设计文档
- “先这样吧” 这类临时口吻
- 需求、设计、实现、规划混在同一段

## 7. 表格使用规范

适合用表格的内容：

- 字段说明
- 权限矩阵
- 状态流转
- 风险清单
- 版本变更

字段表推荐格式：

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| name | string | 是 | - | 名称 |

单元格内容过长时，**应该**改用列表形式替代表格，或将长内容字段拆分为独立小节。**禁止**在单元格内使用 `<br>` 强制换行，以保持 Markdown 源文件可读性。

## 8. 代码块规范

- 命令行使用 `bash`
- JSON 示例使用 `json`
- 配置示例使用对应语言类型
- 示例保持最小可读，不贴过长无关内容

### 8.1 代码块与注释示例

文档中的代码示例应展示注释使用边界：注释解释意图、约束和公共契约，不重复解释代码本身。

**单行注释**适合局部非显然意图或边界条件：

```text
# 保留 1 秒缓冲，避免上游时间戳四舍五入导致重复拉取。
since = last_synced_at - 1s
```

**多行注释**适合复杂流程、状态机、协议、并发或事务约束：

```text
/*
状态只能从 Pending 进入 Running。
失败重试会重新入队，但不能回到 Pending，
否则监控会把同一任务统计为两次创建。
*/
transition(task, Running)
```

**文档注释**适合公共模块、公共类、公共函数、对外接口和脚本入口参数：

```text
/**
 * 创建导出任务。
 * 输入为已验证的筛选条件；返回任务 ID。
 * 副作用：写入任务表，并触发异步 Worker。
 */
createExportTask(filter)
```

禁止在示例中保留大段注释掉的废弃代码。技术债、长期 TODO 和已知问题应写入 `BACKLOG.md` 或对应设计文档。

## 9. 状态与规则表达

建议统一使用以下术语：

- **必须**：强约束，不允许偏离
- **应该**：推荐做法，允许特殊说明后偏离
- **可选**：按需使用
- **禁止**：明确不允许

## 10. 文件命名规范

- 使用英文 `kebab-case`
- 文件名体现主题，不使用 `new-doc.md`、`temp.md`
- 示例：
  - `api-spec.md`
  - `database-design.md`
  - `risk-register.md`
  - `feature-template.md`

## 11. 图表与链接规范

### 11.1 图表

- 架构图、流程图、时序图**应该**使用 Mermaid 代码块内联，便于版本控制与 diff
- 复杂图形可放置到 `assets/` 下，文件名使用 kebab-case，例如 `user-login-flow.png`
- 每张图**必须**有图注（紧跟图下方的一行说明），不要让读者猜意图
- 图中出现的术语**必须**与正文一致

Mermaid 示例：

````markdown
```mermaid
flowchart LR
  A[用户] --> B[网关] --> C[订单服务]
```

图 1：下单请求主链路
````

### 11.2 内部链接

- 跨文档引用**必须**使用相对路径：`design/api-spec.md`，不使用绝对路径或仓库 URL
- 锚点**必须**使用 Markdown 生成的小写 kebab-case：`design/api-spec.md#user-login`
- 每次大改后**应该**运行死链检查（如 `lychee`、`markdown-link-check`）

### 11.3 外部链接

- 外部链接**必须**带完整协议：`https://example.com`
- 易变的外部内容（博客、临时页）**应该**注明访问日期：`https://... （访问于 {{YYYY-MM-DD}}）`

## 12. 架构与页面表达约定

本节约束"架构图"与"页面线框图"两类**内容型文档**的写法，与 § 11 的形式规范（图表/链接）分开。

### 12.1 页面线框图

- 页面结构说明**应该**统一写入 `design/ui-wireframes.md`
- 页面线框图**应该**使用 ```` ```text ```` 代码块表达主布局，不要求几何精确，但要求语义稳定、可读
- 若页面存在多个主要区域，**应该**直接写清每个区域的名称、职责与主交互流向
- 弹窗、抽屉、浮层等次级结构写入"关键交互"，不要冒充主布局区块

### 12.2 架构设计表达

- 总体架构说明**应该**统一写入 `design/architecture-overview.md`
- 文档中统一使用 `三层架构` 表示 `表现层 / 业务层 / 数据层`，避免使用含义不稳定的"`三分架构`"表述
- 若系统采用 `三层架构`，**必须**写清表现层、业务层、数据层的边界与依赖方向
- 若系统采用 `六边形架构`，**必须**写清核心领域、输入端口、输出端口、输入适配器、输出适配器
- 六边形架构中，领域核心**必须**不直接依赖数据库、HTTP 框架、消息队列、第三方 SDK
- 端口与适配器关系**应该**用表格或 Mermaid 表达，避免只写概念、不写落点
- 采用或切换 `三层架构`、`六边形架构` 时，**应该**同步新增或更新 ADR，说明原因、边界和迁移策略

## 13. 数值与版本表达

### 13.1 版本号

- 语义化版本统一写作 `v{major}.{minor}.{patch}`，例如 `v1.2.0`
- 预发布版本用 `-` 分隔：`v1.2.0-rc.1`
- API 版本在 URL 中用 `v1`、`v2`，文档正文引用时统一为 `API v1`

### 13.2 长度与容量

- 字符长度统一写作 `最大 255 字符` 或表格中 `max_length: 255`
- 存储容量使用 IEC 单位：`KiB / MiB / GiB`；面向用户的文案可用 SI：`KB / MB / GB`
- 时间区间使用 ISO 8601 Duration：`PT30S`、`P1D`，或明确"30 秒"、"1 天"

### 13.3 日期与时间

- 日期统一 `YYYY-MM-DD`
- 时间戳统一 ISO 8601 带时区：`2026-04-17T10:30:00+08:00`
- 文档中不使用相对时间（"上周"、"下个季度"），**必须**写绝对日期

## 14. 中英文与标点

- 中英文混排时，英文/数字与中文之间**应该**留半角空格：`使用 Mermaid 绘制`
- 正文**必须**使用全角中文标点：`，。；：？！`
- 代码块、文件名、URL、占位符**必须**使用半角字符
- 专有名词保留原始大小写：`GitHub`、`JavaScript`、`PostgreSQL`

## 15. 维护建议

- 每次大改后同步更新时间
- 文档长期无人维护时标记 `Deprecated` 或 `Archived`
- 评审通过后的文档尽量减少随意改动
- 标记为 `Deprecated` 的文档**应该**在头部补充：
  - `> Deprecated since：{{YYYY-MM-DD}}`
  - `> Replaced by：{{REPLACEMENT_DOC_PATH}}`（若有替代文档）
