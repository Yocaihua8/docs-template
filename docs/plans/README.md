本目录存放 AI 编码助手在执行 BACKLOG 任务时生成的**任务计划文件**。

## 1. 定位与边界

| 文档 | 面向 | 内容 | 生命周期 |
|------|------|------|----------|
| `../BACKLOG.md` | 团队 | 要做什么、优先级、规模 | 长期维护 |
| `../adr/*.md`（启用 `architecture` pack 时） | 团队 | 为什么这样设计 | 永久保留 |
| `../devlog/YYYY/MM/*.md` | 开发者 | 做了什么、卡在哪 | 持续保留在年月目录 |
| `./*.md`（本目录） | AI + 执行者 | 怎么做、任务拆解、完成标准 | **任务完成后删除** |

**一句话区分**：BACKLOG 是"要做什么"，DevLog 是"做到哪了"，**Plan 是"这次怎么做"**；启用 `architecture` pack 时，ADR 记录"为什么这样定"。

只在需要多步恢复、跨模块协调或复杂变更时使用 plan；局部修订可直接记录结果。知识、接口、数据与发布的既有约束仍按项目规则执行。

## 2. 文件命名规范

**主动创建**（推荐，B-ID 作为前缀，关联关系从文件名即可看出）：

```text
{B-ID}-{slug}.md
```

示例：`B-001-order-export.md`、`B-007-auth-refactor.md`

**工具自动生成**（Claude Code、superpowers 等工具产生，接受日期命名）：

```text
{YYYY-MM-DD}-{slug}.md
```

示例：`2026-05-07-student-dashboard.md`

> 命名格式不同，但**BACKLOG 同步要求完全相同**。工具生成后必须补做 § 4 的同步操作。

## 3. 生命周期

1. 关联实际 BACKLOG 条目，并核对本任务涉及的 Active / Interrupted plan 和未提交改动。重叠章节或设计冲突需要明确等待、合并、覆盖或分区；独立章节可记录分区后继续。
2. 创建或恢复计划，写明目标、影响范围、必要前置条件和完成标准。工具生成的 plan 同样补充状态与关联。
3. 用户确认范围后连续实施；在可验证阶段结束、关键决策或中断时更新勾选、状态快照和下一步。是否提交由用户授权和 Git 规则决定，不为每个勾选项强制提交。
4. 中断时保留 plan，标记 Interrupted，并记录未提交改动和剩余验证。恢复时核对当前源码与记录，不因发现一个旧计划就自动恢复无关任务。
5. 完成任务约定的实施、验证及文档回流后更新 BACKLOG 并删除完成的 plan。无法完成必需验证时保留未完成状态并说明阻塞，记录失败本身不等于验收通过。

Git 合并或发布只有在任务明确包含时才是完成条件；它们的独立审批与质量门不由 plan 授予或豁免。

## 4. 何时必须回流

删除 plan 文件前，检查以下事项：

| 内容 | 回流目标 |
|------|----------|
| 功能行为变更 | `../features/<name>.md` |
| 接口变更 | 启用 `api` pack 时更新 `../design/api-spec.md`；否则更新项目实际存在的功能或契约文档 |
| 数据或持久化结构变更 | 启用 `data` pack 时更新 `../design/database-design.md`；否则更新项目实际存在的数据说明或功能文档 |
| 重大技术决策 | 启用 `architecture` pack 时更新 `../adr/<ADR-ID>.md` 与 `../adr/README.md`；否则回流到实际存在的长期设计或功能文档 |
| 遇到的问题与规避 | `../BACKLOG.md`（已知问题）或 `../devlog/YYYY/MM/` |

## 5. 模板

新建计划时复制 `plan-template.md`，按模板字段填写。
