# 合并冲突处理手册

> 状态：Draft
> Owner：{{OWNER}}
> Last Updated：{{CURRENT_DATE}}
> Scope：{{TEAM_OR_PROJECT}}
> Related：`branch-conventions.md`、`team-collaboration.md`

本文档用于多人或多分支并行开发时处理合并冲突。目标是识别冲突类型、确认权威契约并把问题退回对应负责人，而不是让集成负责人替所有人修业务缺陷。具体分支名、评审入口和自动化能力以项目实际配置为准。

## 1. 适用场景

| 场景 | 是否适用 | 说明 |
|------|----------|------|
| 多人同时修改入口、配置、清单或模块装配 | 是 | 先确认合并顺序和权威来源 |
| 同一模块或公共契约出现不兼容修改 | 是 | 先回到已启用的功能、接口或设计文档确认边界 |
| 依赖锁文件、迁移、生成物或配置同时变化 | 是 | 由对应能力负责人按工具和项目规则重新生成或排序 |
| 测试口径不一致 | 是 | 先统一共同验收口径，再修改测试 |
| 页面、组件或公共样式冲突 | 仅启用 `frontend` pack 时 | 分别回到页面模块契约、组件 API 契约或样式边界确认 |
| 单人小修复且无冲突 | 否 | 按普通变更评审流程处理 |

## 2. 分支约定

项目应先在 `branch-conventions.md` 中确定目标分支和命名策略；下表中的占位符不得直接当作真实分支名执行。

| 分支 | 用途 | 负责人 | 规则 |
|------|------|--------|------|
| `{{TARGET_BRANCH}}` | 当前任务的目标分支 | {{TARGET_BRANCH_OWNER}} | 不直接提交未经项目规则允许的变更 |
| `integration/{{TOPIC}}` | 集中模拟合并和修复集成冲突 | {{INTEGRATION_OWNER}} | 只做冲突定位、顺序调整和必要集成修复 |
| `{{FEATURE_BRANCH}}` | 功能、修复、文档或维护任务分支 | {{MODULE_OWNER}} | 只修改约定范围内的文件 |

创建临时 integration 分支示例：

```bash
git fetch origin
git switch {{TARGET_BRANCH}}
git pull --ff-only origin {{TARGET_BRANCH}}
git switch -c integration/{{TOPIC}}
```

## 3. 只读模拟合并

只读模拟合并用于发现冲突，不用于直接产生业务修复提交。若命令产生工作区改动，必须执行 `git merge --abort` 或删除确认不再需要的临时分支。

| 步骤 | 命令 | 预期 |
|------|------|------|
| 确认工作区干净 | `git status --short` | 无未提交改动 |
| 创建临时集成分支 | `git switch -c integration/{{TOPIC}}` | 位于最新目标分支 |
| 模拟合并任务分支 | `git merge --no-commit --no-ff {{FEATURE_BRANCH}}` | 自动合并或暴露冲突 |
| 记录冲突文件 | `git status --short` | 看见冲突路径 |
| 放弃模拟结果 | `git merge --abort` | 回到模拟前状态 |

如果只是快速查看两个分支是否会冲突，可使用：

```bash
git merge-tree $(git merge-base {{TARGET_BRANCH}} {{FEATURE_BRANCH}}) {{TARGET_BRANCH}} {{FEATURE_BRANCH}}
```

该命令不修改工作区，但输出不如真实 merge 直观。

## 4. 冲突分类

| 冲突类型 | 典型文件或内容 | 判断标准 | 处理方式 |
|----------|----------------|----------|----------|
| 结构冲突 | 入口、目录清单、模块注册、路由或装配配置 | 多人调整相同层级、顺序或启用状态 | 由集成负责人根据权威功能或设计文档确认最终装配 |
| 契约冲突（含项目存在 API 时的 API 冲突） | 公共 API、CLI 参数、配置格式、数据结构、接口或类型定义 | 同一名称的职责、输入、输出或兼容规则不同 | 退回契约 Owner，先更新已启用的契约文档和测试 |
| 依赖与生成冲突 | 依赖锁文件、迁移、代码生成结果、构建配置 | 手工拼接会破坏工具顺序或生成一致性 | 按项目工具重新生成；迁移顺序由数据或发布负责人确认 |
| 测试冲突 | 单元、集成、端到端或快照测试 | 测试反映个人方案，不是团队共同验收口径 | 退回验收负责人，先统一预期行为 |
| 文档冲突 | 功能说明、契约、README、BACKLOG 或变更描述 | 文档描述互相矛盾 | 由对应文档 Owner 确认权威版本 |
| 前端结构 / 组件 / 样式冲突 | 页面编排、组件 API、公共样式 | 仅在启用 `frontend` pack 且存在对应资产时适用 | 分别回到 `../design/page-module-contract.md`、`../design/component-api-contract.md` 或项目样式边界确认 |

未启用 `frontend` pack 时，不要求创建或引用页面模块契约、组件 API 契约，也不使用前端专属分类替代项目真实的冲突类型。

## 5. 退回对应负责人规则

| 问题 | 退回对象 | 需要补交的内容 |
|------|----------|----------------|
| 越过文件边界 | 变更作者 | 恢复越界文件，或补充范围变更说明并重新评审 |
| 公共契约不一致 | 契约或模块负责人 | 更新实际启用的契约文档、兼容性说明和测试 |
| 入口或装配顺序冲突 | 集成负责人 | 确认最终顺序、启用状态和权威来源 |
| 依赖、迁移或生成顺序冲突 | 对应能力负责人 | 使用项目工具重新生成，并记录顺序与验证结果 |
| 页面、组件或公共样式冲突 | 前端对应负责人 | 仅启用 `frontend` pack 时，更新对应页面 / 组件契约或样式边界 |
| 测试口径冲突 | 验收负责人 | 更新共同验收标准，删除仅代表个人方案的断言 |
| 业务缺陷 | 原模块负责人 | 修复业务逻辑并补充相关测试 |

集成负责人不负责替模块负责人修业务缺陷。集成负责人只负责：

- 判断冲突类型。
- 维护临时集成分支和合并顺序。
- 根据权威契约调整入口、模块注册或统一装配。
- 退回不符合范围或契约的改动。
- 记录冲突处理结论。

## 7. 合并前检查清单

- [ ] 已在 integration 分支或其他临时分支完成模拟合并
- [ ] 每个冲突都已确认类型、负责人和权威来源
- [ ] 入口、模块注册或公共契约冲突已由对应 Owner 确认
- [ ] 依赖锁文件、迁移或生成物已按项目工具和顺序处理
- [ ] 测试文件体现团队共同验收口径
- [ ] 启用 `frontend` pack 时，页面和组件冲突已回到实际存在的对应契约确认
- [ ] 业务缺陷已退回对应负责人，不由集成负责人兜底
- [ ] 最终变更描述记录了冲突处理结论和验证结果
