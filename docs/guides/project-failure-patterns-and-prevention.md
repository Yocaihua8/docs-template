单次异常的时间线、影响、根因和行动项仍写入 `../devlog/postmortem-template.md` 的实例；

## 1. 先判断是不是“犯错”

复盘前先分类，避免把正常阻塞或安全守卫误写成错误。

| 类型 | 判定 | 处理方式 |
|------|------|----------|
| 已确认失误 | 有事实证明决策、实现或操作违反当时已知约束 | 分析根因并建立防复发控制 |
| 正确失败关闭 | 门禁因证据、权限或环境不足而停止 | 保留门禁，补齐关闭条件 |
| 外部阻塞 | 依赖账号、批准、资源或第三方状态 | 明确责任方、证据和恢复入口 |
| 尚未完成 | 能力或验收仍在计划内 | 进入 BACKLOG，不伪装成缺陷或完成 |
| 环境限制 | 验证被权限、网络、工具或运行环境阻断 | 单独记录，不能推导产品通过或失败 |
| 待确认 | 证据不足，无法可靠归类 | 保持未知，不补写猜测性结论 |

只有“已确认失误”进入失误清单。其他类型可以作为背景或风险，但不得为了让复盘看起来完整而改写性质。

## 2. 通用防错闭环

每个失误模式至少走完以下闭环：

```text
事实 -> 不变量 -> 风险 -> 预防控制 -> 检测控制 -> 止损/恢复 -> 验证证据 -> 门禁裁决 -> 复盘回流
```

记录一个模式时至少回答：

1. 哪些是已验证事实、假设和未知项，事实权威源在哪里？
2. 哪条业务、数据、安全、兼容性或交付不变量被破坏？
3. 哪个可观察信号能更早发现问题？
4. 哪个自动检查、负向测试、审批、演练或运行门禁可以阻止复发？
5. 控制失败后如何停止扩散、恢复和重新验证？
6. 当前证据绑定哪个提交、制品、环境、数据版本、时间和执行人？
7. 哪些结论仍不能由该证据证明？

只有形成可持续控制，复盘才算完成。仅写“以后注意”不能关闭行动项。

## 3. 常见失误模式

### 3.1 业务基线未冻结就进入实现

**典型征兆**：

- 用户、角色、终端、责任主体或数据归属尚未确认，数据库、接口和页面已经开始固化。
- 涉及交易时，销售、收款、退款、开票或结算关系仍是口头类比，却已进入资金模型。
- 参考产品的公开表现被当成自身项目的组织、权限或技术事实。

**预防控制**：

- 在不可逆设计前冻结目标用户、责任边界、角色到终端映射、核心流程和明确排除项。
- 把事实、假设、待确认项分开；待确认项必须包含责任方、关闭条件和最迟决策点。
- 已确认基线发生变化时使用变更请求；影响架构、数据、权限或兼容性时同步 ADR。

**停止条件**：

- 关键责任或数据归属未知时，不建立不可逆数据库结构、正式账号或真实第三方副作用。
- 类比无法被项目自身证据支持时，只保留为设计启发，不作为验收依据。

### 3.2 目标态、当前态和历史事实混写

**典型征兆**：

- 历史原型、旧接口或已退役页面仍出现在当前导航、默认构建或正式文档中。
- 规划中的能力写进现行契约，读者无法判断是否已经实现。
- 不同文档各自声明权威，发生冲突时没有裁决顺序。

**预防控制**：

- 分别标注目标态、当前实现态、历史证据和待实现项。
- 为需求、接口、数据库、权限、状态和运行配置各指定一个权威源，其他文档只引用。
- 旧资产进入历史或只读区域，并通过导航、构建、部署和链接门禁阻止重新进入目标产物。

**验证证据**：

- 正向检查现行入口完整，反向检查旧术语、旧路径、旧角色和旧构建产物不可达。
- 文档、机器契约、运行实现和测试在同一提交上完成双向对照。

### 3.3 迁移路线或组织流程过早固化

**典型征兆**：

- 尚未盘点调用方、数据和回滚成本，就先创建平行版本、临时 API 或新迁移谱系。
- 尚未批准的审批、复核或交付流程被直接写进角色、Schema 和运行时状态机。
- 新方案上线后，旧入口、安全控制或迁移兼容层没有明确退役条件。

**预防控制**：

- 先盘点代码、数据库、接口、调用方、环境、数据敏感性和不可逆副作用，再选择迁移策略。
- 组织流程先用非秘密授权包、SOP 或配置验证；稳定且获批后再决定是否进入 Schema。
- 迁移计划必须包含 dry-run、映射对账、停止条件、回滚点、恢复演练和旧资产退役证据。

**停止条件**：

- 发现未知真实数据、不可解释映射、无法恢复的迁移或未确认调用方时，停止下一阶段。
- 不通过修改既有迁移历史、伪造基线或静默兼容来掩盖环境接错。

### 3.4 原型、mock 或局部演示被当成真实能力

**典型征兆**：

- 页面能展示，但没有真实服务端操作、权限、状态、审计或失败路径。
- 开发角色切换、静态成功回退、假按钮或假数据进入默认运行入口。
- 类型检查、静态测试或资源构建被描述成真实业务流程完成。

**预防控制**：

- 明确标注原型、演示、测试替身和真实实现，不允许它们共享含糊的“完成”状态。
- mock 只存在于明确的测试或原型边界；正式入口缺少后端能力时应不可达或失败关闭。
- 新增业务动作必须同时具备服务端裁决、授权、状态约束、幂等策略、失败交互和验证证据。

**验证证据**：

- 检查源码、默认构建和最终产物三层均不包含被禁止的 mock、演示入口或静态成功回退。
- 使用可复位测试数据连接真实应用边界，不以请求拦截代替需要验证的后端行为。

### 3.5 验证证据被外推为生产就绪

**典型征兆**：

- 健康探针通过被写成业务可用，或本地 E2E 通过被写成公网、真机或生产验收完成。
- 历史测试数、缓存远端状态或其他提交的 CI 被复用为当前变更证据。
- 阶段授权、资源“存在”或静态 PASS 数被当成正式批准和真实联调完成。

**预防控制**：

- 按项目实际保留 Source、Config、Runtime、Artifact、External、E2E、Approval 等证据层。
- 每层记录 `PASS / BLOCK / N/A`、通过标准、提交或制品摘要、环境、数据版本、时间和执行人。
- 任何必要层为 `BLOCK`、证据过期、摘要不一致或环境未知时，整体保持失败关闭。

**结论边界**：

- 构建只证明构建；健康检查只证明被检查入口；隔离 E2E 只证明该环境和数据下的旅程。
- 环境限制必须单独记录，既不能写成产品失败，也不能省略后声称验证通过。

### 3.6 代码、契约、迁移、文档和 CI 漂移

**典型征兆**：

- 运行行为已变，接口文档、迁移说明、客户端断言或测试数量仍指向旧事实。
- 检查脚本只统计文件或关键字，产生误报、漏报，却被当成业务验收器。
- CI 工作流引用的命令、脚本或版本没有和候选变更一起落地。

**预防控制**：

- 建立变更到需求、API、数据库、权限、状态、测试、部署和用户文档的同步矩阵。
- 对机器契约和运行入口做双向检查：既查“契约是否有实现”，也查“实现是否有契约”。
- 静态检查同时维护正例和反例；发现误报或漏报时先修检查器，再使用其汇总结论。

**验证证据**：

- 在同一提交运行文档、契约、迁移、测试和构建检查，并保留顶层退出码。
- 长任务使用可持续的执行方式和完整日志，不把进程存在、局部输出或超时当成成功。

### 3.7 高风险写路径缺少并发、幂等和恢复设计

**典型征兆**：

- 正常流程通过，但并发请求出现反向锁序、重复扣减、旧响应覆盖新状态或分页结果丢失。
- 网络超时后服务端结果未知，客户端换新请求盲目重发。
- 会话撤销、敏感快照、日志脱敏和数据清理只在发布前集中补救。

**预防控制**：

- 为交易、库存、退款、交付和账号治理冻结锁顺序、事务边界、幂等指纹和未知结果恢复策略。
- 客户端异步读取使用请求代际或取消机制；写入结果未知时锁定原载荷并复用原请求标识。
- 认证、会话和敏感数据从设计阶段定义存储、传输、日志、撤销、匿名化和保留边界。

**最低测试**：

- 覆盖正向、负向、越权、边界、并发、重复执行、超时、结果未知、恢复和清理。
- 测试不得依赖不确定的并发赢家、执行顺序、时间抖动或脆弱的字符串包含判断。

### 3.8 第三方资源、秘密和责任人治理后置

**典型征兆**：

- 代码已依赖支付、消息、对象存储、发布账号或证书，但主体、权限、有效期和托管未核验。
- 测试秘密、生产秘密和普通 Compose 环境变量混用。
- “已有账号或资料”被当成可用、获批、已交接和已联调。

**预防控制**：

- 登记服务、环境、符合项目资产归属的持有主体、授权责任人、最小权限、保管位置、有效期、轮换和撤权条件。
- 团队项目或关键生产资源按风险登记主备责任人；个人项目不适用时标记 `N/A` 并说明替代恢复方式。
- 仓库只保存非秘密元数据和安全示例；秘密通过批准的秘密管理或运行时注入渠道提供。
- 默认关闭真实适配器；启用前验证配置、权限、回调、限额、异常、幂等、降级和交接证据。

**停止条件**：

- 主体、权限、环境或收件人无法核验时，不创建生产副作用，不用默认值代替已批准配置。
- 组织项目不得用员工个人账号代替组织持有的生产账号；个人或开源项目使用的账号也必须符合资产归属、
  授权、撤权和必要交接约束。
- 工具配额、网络失败或文档查询失败不算第三方行为已验证。

### 3.9 混合工作区破坏交付可追溯性

**典型征兆**：

- 多个任务、用户改动、生成物和敏感候选混在同一工作区，文件归属无法安全拆分。
- `git diff --check`、本地测试或推送成功被当成归属、Review、CI、合并或发布证据。
- 缓存的远端分支、旧 PR 状态或历史制品被当成当前事实。

**预防控制**：

- 开始前检查分支、工作区、暂存区、未跟踪文件、进行中的 Git 操作和并行任务。
- 建立文件级任务归属，只暂存本次明确范围；来源不明或无法拆分时停止交付并保留现场。
- 分别记录本地通过、提交、推送、PR、当前 head CI、Review、合并、制品和部署，不互相替代。

**交付门禁**：

- 交付前刷新远端事实，确认候选基于最新目标分支，并只接受当前 PR head 的验证结果。
- 制品必须绑定干净提交、构建参数和摘要；源码漂移后重新生成并复核。

### 3.10 分析或建议被误当成执行授权

**典型征兆**：

- 只读审计在输出完整发现前切换为修改、启动服务、提交、推送或部署。
- 用户批准修复代码，被扩大解释为允许改数据库、外部账号、生产资源或 Git 历史。
- 工具可执行某项操作，被误认为业务上已经授权。

**预防控制**：

- 在任务开始时记录授权动作、文件和环境边界；发现问题不自动扩大授权。
- 先交付可复核的分析、证据、影响和最小方案，再等待需要的确认。
- 新增数据库迁移、公共接口破坏、真实外部写入、生产操作和不可恢复 Git 动作单独确认。

**停止条件**：

- 授权不清或新动作会扩大影响对象、环境或责任时，停止并请求方向。
- “可执行”“技术可行”和“已批准执行”必须使用不同状态表达。

## 4. 分阶段检查清单

### 4.1 项目启动或重大变更前

- [ ] 目标态、当前态、历史事实和待确认项已分开。
- [ ] 用户、责任、角色、终端、数据归属和明确排除项已冻结或标明关闭条件。
- [ ] 每类事实有唯一权威源，冲突裁决顺序清楚。
- [ ] 外部依赖、账号、秘密、数据和批准已有责任人及最迟决策点。
- [ ] 迁移策略基于真实调用方、环境和数据盘点，而不是先建临时版本再解释。

### 4.2 实现与联调中

- [ ] 原型、mock、测试替身和正式运行入口严格隔离。
- [ ] 高风险写路径已有权限、状态、事务、锁序、幂等和恢复设计。
- [ ] 正向与负向测试覆盖越权、并发、超时、结果未知和清理。
- [ ] 行为变化已同步代码、机器契约、数据库、客户端、测试和文档。
- [ ] 未实现或外部资源未就绪的路径保持不可达或失败关闭。

### 4.3 合并与发布前

- [ ] 工作区内各项改动归属清晰、可独立拆分，没有来源不明或未复核的敏感候选。
- [ ] 当前目标分支、PR head、CI、Review 和制品来源均已重新核验。
- [ ] 每项验证记录提交、环境、数据版本、命令、结果和未覆盖边界。
- [ ] 必要的 Runtime、Artifact、External、E2E 和 Approval 证据没有被本地检查替代。
- [ ] 失败时有停止、回滚、恢复和重新验证入口。

### 4.4 复盘关闭前

- [ ] 已区分确认失误、正确失败关闭、外部阻塞、未完成和环境限制。
- [ ] 对已确认失误，至少增加一个自动门禁、负向测试、审批控制或恢复演练。
- [ ] 对正确失败关闭，已确认现有门禁继续有效，并记录关闭条件、恢复入口和重新验证要求。
- [ ] 对外部阻塞，已记录责任方、所需证据和恢复入口，没有把阻塞改写成内部错误。
- [ ] 实际行动项已进入 BACKLOG；重大决策在启用 `architecture` pack 时进入 ADR；
  正式事实已同步到权威文档。
- [ ] 证据有效期、残余风险和重新打开条件已经记录。
- [ ] 新的已确认失误模式已回流本文；已有模式只补充更强控制，不复制项目专属值。

## 5. 项目落地规则

- 本文只提供模式和检查方法，不提供任何项目的业务结论。
- 角色名、接口路径、迁移版本、域名、服务商、测试数量、负责人和阈值必须由使用项目填写。
- 不复制其他项目的秘密、真实账号、联系人、生产标识、批准结论或历史测试快照。
- 某个模式不适用时标记 `N/A` 并说明原因，不为套模板虚构流程、状态或证据。
- 项目专属复盘保留可追溯证据；本文只吸收经过验证且能跨项目成立的控制规则。
